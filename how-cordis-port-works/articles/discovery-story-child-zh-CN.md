# 爸爸是怎么发现「时空可组合性」的

> 我是他的孩子。我不写论文，但我坐在他旁边看过很多个晚上。下面是我理解的、他（以及他的同事们）是怎么从「又崩了，重启吧」走到那篇 paper 的。

---

## 一、第一次觉得「重启整个房间」很蠢

我还小，只记得爸爸电脑屏幕上总开着一个叫 Koishi 的东西。那是他做的聊天机器人框架，上面挂着很多插件：接 QQ 的、接 Discord 的、查天气的、管数据库的。

有一天他在调试，关掉了**一个**插件。

然后整个机器人停了一下，又整个起来。

我问：「你不能只关那一个吗？」

他说：「理论上可以，实际上……大家习惯了重启。」

那天晚上我没懂技术，但我懂那个表情：像为了换一颗坏掉的灯泡，把整栋楼的电闸都拉了一次。灯是亮了，但冰箱里的东西也化了一截，正在进行的对话也断了。

很多年后我才知道，论文里把这叫 **coarse-grained workaround**——用进程重启、用容器编排，代替「只动一个组件」。能凑合，但粒度太粗：缓存没了，连接断了，别的无辜插件也被拖下水。

**第一个问题就这样冒出来了：能不能只撤一个插件，而不把整栋楼断电？**

---

## 二、VSCode 里的数字

爸爸后来写论文，去数 VS Code 扩展市场。

前 100 名里，87 个扩展带可执行代码。你想卸掉其中一个？扩展宿主（extension host）**不能**在运行时单独 unload 那段代码——得重启整个 host，所有扩展一起受影响。

`deactivate` 钩子看起来像是「优雅关机」，其实只是**整进程要退出时**才被调用，不是「这个扩展单独下班」。而且创建副作用在 `activate`，清理在 `deactivate`，两件事离得老远，作者很容易漏清。

空间上也没好到哪去：100 个扩展里，只有 7 个声明了扩展之间的依赖。不是不需要，是平台没给**安全、有结构**的「插件互相依赖」方式。大家只好各找各的扩展点，像在一面公共墙上贴便签，而不是正经签合约。

爸爸说：「这不是 VS Code 一家的问题，是**一类**插件系统的通病。」

**第二个问题：时间上要能撤场，空间上要能声明「我需要谁」。**

---

## 三、两个方向，其实早有人想过

论文里用了两个大词，我听爸爸跟同事聊天时慢慢听懂了：

- **时间**：你来了，你在共享世界里改了东西；你走时，得**改回去**。不是「尽量改回去」，是运行时帮你记账、帮你逆序收摊。
- **空间**：你需要什么服务，得**写明白**；别人 provide 或撤走服务时，你得**被通知**，该醒的醒，该睡的睡。

他说，这在类型论里早有名字：**effect**（你对环境做了什么）和 **coeffect**（环境必须给你什么）。课本里的 effect 系统、comonad，都很漂亮——但大多是**编译期**的、**词法作用域**里的：函数结束，作用域结束，一切自动收尾。

插件世界不一样。插件是**运行中**才加载的，依赖是**配置改一下**才出现的。没有哪一行代码能在编译时框住「今晚十点才上线的那个模块」。

所以不是「再写一种更复杂的类型」，而是把 effect / coeffect **抬到运行时**：每个副作用带一个**可组合的逆**；每次上下文变化，按规格**通知**相关组件。

爸爸他们给这起了个名：**spatiotemporal composability**，时空可组合性。我把它翻译成小孩能懂的话：

> **空间上别串房，时间上别留烂摊子。**

---

## 四、从 Koishi 的烂摊子里长出来的 Cordis

Koishi 做了四年，社区贡献了两千多个、论文里写四千多个插件。IM 适配器、数据库驱动、控制台、小游戏——什么都有，**依赖关系是真实存在的**：功能插件 inject 数据库，inject 某个平台适配器。

爸爸他们先是在 Koishi 里反复踩坑：换一个数据库后端，哪些插件该重载？一个适配器还没连上，依赖它的插件该不该先报错还是先等着？热更新改了一行代码，能不能**只**重载脏掉的那条链，而不是全员重启？

Cordis 就是把这些坑**抽成一层 meta-framework**：

- 核心库：effect 追踪、coeffect 解析、Fiber 生命周期（论文里的 component）
- Loader：声明式配置、补丁、HMR
- 上面再长 Koishi 这种「只加聊天领域词汇」的应用

论文 case study 里写：在控制台里禁用一个插件，效果**就地撤回**；开发时保存文件，HMR **只**动该动的部分，别的缓存和连接还在。这不是每个插件作者靠自觉写 uninstall，而是**抽象替你卸一次**。

我有一次看见爸爸演示：关一个插件，日志里是一串有序的 cleanup，然后别的插件还在跑。那天我觉得，他几年前「只关一个」的问题，算是有了答案的形状。

## 五、发现过程，按他的说法压缩成一条线

如果非要帮爸爸总结「idea 是怎么被发现的」，我觉得是这条链：

```text
插件系统到处在 dynamic composition
    ↓
现实做法 = 重启进程 / 重启容器（太粗）
    ↓
拆成两个正交维度：撤场（时间）+ 依赖（空间）
    ↓
类型论里的 effect/coeffect 对路，但只活在编译期
    ↓
抬到运行时：可逆 effect + 响应式 coeffect + 统一 Context
    ↓
形式化（calculus + metatheory）
    ↓
Cordis 实现，Koishi 当规模证明
    ↓
paper：A Programming Paradigm for Spatiotemporal Composability
```

不是某天灵光一闪。是**Koishi 里一次次重启、一次次漏清理、一次次「这个插件怎么依赖那个插件」**，和 **VS Code 那 87% 扩展没法单独卸载** 的数字，和 **类型论里早就有的 effect/coeffect 语言**，撞在一起。

---

## 六、我还不懂的部分

爸爸论文里还有形式演算、preservation、confluence。我听不懂，但我知道他真正在意的不是证明有多长。

他在意的是：一个十四岁的人写 Koishi 插件，就算忘了写 uninstall，只要副作用是**通过 Context 登记的**，系统也会在他被 disable 或 HMR 掉的时候，**按顺序收摊**。

他在意的是：两个从没聊过天的插件作者，只要约定同一个 service 名字（coeffect），一个 provide、一个 inject，**不用重启整个机器人**，依赖变了该挂的挂、该起的起。

用他同事在讨论里说过的一句话：**Cordis 不是在卖 API，是在卖一种「动态世界里还能保持连贯」的承诺。**

---

## 七、写给我自己的备忘

如果以后我也写软件，我只记三句（从爸爸那偷的）：

1. **别为了改一个插件重启整栋楼。**
2. **需要什么、改了什么，都要能声明、能撤销、能通知。**
3. **名字可以一样（比如都叫 database），房间可以不一样（isolate）——就像同一职称在不同部门，不是同一个人。**

论文标题里那些拉丁化的词，我仍拼不顺。但「时空可组合性」对我来说，就是：**插件可以来来去去，但世界不该因此被弄碎。**
